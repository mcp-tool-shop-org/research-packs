## Section 07 — Metadata and off-chain durability

**Layer contribution:** Off-chain content reachability — where the pack's central thesis lives. URI on-chain + content unavailable off-chain = nominal token, no semantic content.

**NFTokenMint as the on-chain reference point.** The NFTokenMint transaction type includes fields for specifying additional information and issuing the token on behalf of another account [claim:clm_517d67dc1224_ollama_intern_7]. These three Section-07 accepted claims are deliberately neutral — they describe the on-chain mechanism without conflating "URI on-chain" with "metadata persists."

**IPFS content addressing — identity, not persistence.** CIDs are based on the content's cryptographic hash [claim:clm_d6c57c6845e6_ollama_intern_2]. Any difference in the content will produce a different CID [claim:clm_d6c57c6845e6_ollama_intern_3]. CIDs contain the hash and the codec of the data [claim:clm_d6c57c6845e6_ollama_intern_5]. (The accepted claim "CIDs will not match the hash of the data" [claim:clm_d6c57c6845e6_ollama_intern_6] is preserved verbatim within its source's frame; the source's surrounding prose makes clear that direct hash and CID differ in encoding even though the CID is hash-derived. The synthesis preserves the claim as stated and does not widen.)

**IPFS pinning — the persistence layer.** Pinning is the mechanism that allows you to tell IPFS to always keep a given object somewhere, typically your local node [claim:clm_37c1413248e9_ollama_intern_2]. Objects added through ipfs add are pinned recursively by default [claim:clm_37c1413248e9_ollama_intern_3]. The pin ls command will list all objects that are pinned to your local storage [claim:clm_37c1413248e9_ollama_intern_4]. A pinned object cannot be garbage-collected [claim:clm_37c1413248e9_ollama_intern_5]. You can use the 'pin rm' command to unpin a file from IPFS [claim:clm_37c1413248e9_ollama_intern_6]. Pinning is opt-in; the absence of pinning is the failure mode.

**IPFS persistence economics.** Pinning services are paid services that allow users to store data on a remotely hosted IPFS node and retrieve it whenever they want, but the content may be lost if the sponsor stops [claim:clm_0b01dd18d515_ollama_intern_6]. Filecoin is a decentralized storage network where storage providers rent their storage space to clients, with an agreement called a deal specifying the data to be stored, duration, and other terms [claim:clm_0b01dd18d515_ollama_intern_7]. Filecoin provides a reliable, long-term storage solution but has limitations like slower retrieval than IPFS pinning services and minimum file size requirements [claim:clm_0b01dd18d515_ollama_intern_8]. There are tools and service providers that help simplify storing content on IPFS while persisting it via Filecoin, by acting as both IPFS pinning services and Filecoin storage platforms [claim:clm_0b01dd18d515_ollama_intern_9]. Combined IPFS + Filecoin solutions periodically bundle data and create deals with reputable Filecoin storage providers to ensure long-term availability [claim:clm_0b01dd18d515_ollama_intern_10]. Many IPFS + Filecoin solutions include API client libraries and web interfaces to make it easy for developers to integrate the technology into their applications [claim:clm_0b01dd18d515_ollama_intern_11]. Layered persistence — IPFS pinning + Filecoin deals — is the operator-side mitigation for off-chain content loss.

## Cross-section synthesis dependency map

The seven layers depend on each other as follows:

- **Layer 6 conditions Layers 1-5.** Every paradigm-defining amendment (XLS-0020 for NFTokens [claim:clm_515596050b06_ollama_intern_1], MPTokensV1 for MPTs [claim:clm_90368c8bfc17_ollama_intern_2], NonFungibleTokensV1_1 for NFTokenMint/Offer/AcceptOffer [claim:clm_517d67dc1224_ollama_intern_4] [claim:clm_71ee1ec187f7_ollama_intern_3] [claim:clm_034a20f9fcbf_ollama_intern_3], DynamicNFT for NFTokenModify [claim:clm_ff9fbb4f8527_ollama_intern_3], Clawback [claim:clm_4727592a5328_ollama_intern_5], TokenEscrow [claim:clm_01e8d92d7e53_ollama_intern_3]) gates the existence of a Layer-1-through-5 mechanism. The control plane must check amendment activation status before asserting any feature is available.
- **Layer 6 conditions Layer 7's mutability surface.** NFTokenModify exists only under DynamicNFT [claim:clm_ff9fbb4f8527_ollama_intern_3]. A holder of an NFToken minted before DynamicNFT activation has a fundamentally different durability profile than a holder of one minted with `tfMutable` after DynamicNFT activated.
- **Layer 3 conditions Layer 5.** Reserves must be sufficient for offer creation [claim:clm_71ee1ec187f7_ollama_intern_4]. The base reserve [claim:clm_525532c48160_ollama_intern_4] and owner reserve [claim:clm_525532c48160_ollama_intern_5] together gate transferability.
- **Layer 4 conditions Layer 5.** Freeze state [claim:clm_e1cfbbad4fa5_ollama_intern_9] determines whether escrow can finish; freeze controls [claim:clm_319355bfb19d_ollama_intern_2] [claim:clm_319355bfb19d_ollama_intern_6] [claim:clm_319355bfb19d_ollama_intern_8] determine whether trust-line tokens are even movable.
- **Layer 2 conditions Layer 4.** Account-key control [claim:clm_117260e9e17f_ollama_intern_10] determines whether the issuer can exercise their retained controls. A compromised master key with no offline rotation discipline means the issuer has lost Layer-4 control.
- **Layer 1 determines the entire downstream surface.** The paradigm choice (XRP / trust-line / NFToken / MPT) selects which Layer-3 ledger entries apply [claim:clm_72d8a212a86a_ollama_intern_1] [claim:clm_90368c8bfc17_ollama_intern_2] [claim:clm_f011b0207e63_ollama_intern_2], which Layer-4 controls are in scope, which Layer-5 transactions are valid, and which Layer-6 amendments are relevant.
- **Layer 7 stands alone in repair locus but depends on Layer 4 and Layer 6 for its mutability surface.** The issuer can rotate URIs only if the NFToken was minted mutable AND DynamicNFT is activated [claim:clm_ff9fbb4f8527_ollama_intern_3]. The pack's structural answer to the topic question — what should a creator-side control plane track? — is the seven-layer bundle. Track all seven, monitor cross-layer dependencies, and accept that Layer 7 lives off-chain and must be tracked separately from on-ledger state.
